## Quick reference

UpWaterSort is a **100% offline** Flutter/Dart water-sort puzzle (package `up_water_sort`, Android/iOS primary, portrait only, 100–200 bundled levels). Spec = `PLAN.md`; read the relevant section before any task. Hard rules: no direct network packages (approved transitive exception: `audioplayers` → `http`) and no `INTERNET` permission in release builds; all fonts/audio/levels bundled in `assets/`; `lib/domain/**` is **pure Dart** with zero `flutter/*` imports; state = `provider` + `ChangeNotifier` (Game/Progress/Settings), navigation = Navigator named routes (no Riverpod/Bloc/GoRouter/Flame); rendering = `CustomPainter` + `AnimationController`; `applyMove`/`undoMove` return new states and never mutate inputs; save = a single `shared_preferences` key `save_v1`; solver/generator run in `compute()` at runtime and via `dart run tool/generate_levels.dart` offline. Scope covers the full roadmap, but work strictly in **Phase 0 → 6** order and do not start 1.1/2.0 features before MVP 1.0 is done. Definition of done: `flutter analyze` clean, `flutter test` green, plus the phase's "Done when" in `PLAN.md` §21. Anything in §10 (Open decisions) requires asking the user — never guess.

## 1. Context & current state

- A single-player 2D puzzle game, **fully offline**, 1–3 minutes per level. Dart package `up_water_sort`, display name **UpWaterSort**. Primary targets: Android + iOS; Web/Desktop are optional.
- The repo is **greenfield**: only `PLAN.md` and this file exist — no Flutter project yet, no `lib/`, `assets/`, or `test/`. Start at **Phase 0** (`PLAN.md` §21); never assume code already exists.
- Levels are **pre-generated by a script and bundled in `assets/levels/levels.json`** (commit the JSON too). `par` is computed up front by the BFS solver.
- UI language: `en` by default, `vi` is a 1.1 enhancement.

## 2. Hard constraints — any violation must be fixed before handoff

1. **Absolute offline** (`PLAN.md` §4): no `http`, `dio`, Firebase, AdMob, `google_fonts`, or any network-dependent package **as a direct dependency**; no assets loaded from URLs; fonts bundled in `assets/fonts/` and declared in `pubspec.yaml`; audio/images only under `assets/`; player data only via `shared_preferences`; **no `INTERNET` permission** declared in the release `AndroidManifest.xml`. Final verification is always a playthrough in **airplane mode**.
   > **Approved exception (2026-11-06):** `audioplayers` pulls `http` in transitively (all 1.x–6.x versions do); the app only uses `AssetSource` and has no `INTERNET` permission, so it stays offline. See `PLAN.md` §4. Re-check `flutter pub deps --no-dev` after any dependency change; never add a network package directly.
2. **Pure-Dart domain** (`PLAN.md` §6.1): no file in `lib/domain/` may import `flutter/*` or `package:flutter/*`, use `BuildContext`, or use `Color`. Only `dart:*` and internal imports are allowed. Reason: fast unit tests, and `dart run tool/generate_levels.dart` must work without Flutter SDK binding.
3. **Immutable game rules** (`PLAN.md` §2, §8): tubes are stored **bottom → top**, the last element is the top layer; default `capacity = 4`; each color has exactly `capacity` units; a color is an `int 0..N-1` indexing `kPalette`. `canPour` checks exactly 4 conditions; units poured = `min(topRun(A), capacity - B.length)`; win when every tube is empty or full of a single color; `legalMoves` filters out pointless moves. Every function in `game_rules.dart` must be **pure**: `applyMove`/`undoMove` return a new `Tubes` and never mutate the input.
4. **State management** (`PLAN.md` §11): `provider` + `ChangeNotifier`, exactly 3 controllers — `GameController` / `ProgressController` / `SettingsController` — bootstrapped with `MultiProvider` in `main.dart`. Navigation uses **Navigator named routes**. Never introduce Riverpod, Bloc/Cubit, GetX, or GoRouter.
5. **UI only renders and dispatches events**: widgets and painters contain no game rules and never call `StorageService` / `AudioService` / `LevelRepository` directly; read state via `context.watch` / `context.read`.
6. **Rendering & animation** (`PLAN.md` §13–14): `CustomPainter` + `AnimationController`, **no game engine (Flame)**. During a pour, `busy = true` must lock input; **commit state only after the animation finishes** (`playPourAnimation` → `applyMove`). Complete Level 1 (lift/lower) before starting Level 2 (fly–tilt–pour–return).
7. **Heavy computation**: `Solver` / `LevelGenerator` running inside the app must use `compute()` (Isolate), with a loader and a `maxNodes` cap (default 300,000). Hint runs the solver on the **current state**, not the initial state.
8. **Persistence** (`PLAN.md` §15): exactly one key `save_v1`, one JSON blob; write after every move; wrap `jsonDecode` in `try/catch` → fall back to `SaveData()` (never crash); include a `version` field for migration. **Never rename JSON keys** (`f`, `t`, `c`, `unlocked`, `stars`, `inProgress`, `extra`, `par`, `colors`, …) without a migration.
9. **Layout & performance** (`PLAN.md` §12.3, §20): lock to portrait; use `LayoutBuilder`; wrap each tube in `RepaintBoundary` with an accurate `shouldRepaint`; use `const` constructors wherever possible; `GridView.builder` for 100+ level lists; target 60 fps.
10. **Assets & licensing**: use only royalty-free/CC0 resources and record their sources in `ASSETS_LICENSE.md`. Never commit keystores, `key.properties`, signing files, or credentials.
11. **Quality**: `flutter analyze` clean (including warnings), `flutter test` green, no debug `print` in release builds. Fix the code — do not loosen `analysis_options.yaml` to make it pass.

## 3. Folder structure & dependency direction

The canonical tree is in `PLAN.md` §6.2 — **create exactly that structure**. New files belong in the correct layer; do not invent folders.

```
UI (lib/ui/)  ──►  Controllers (lib/controllers/)  ──►  Domain (lib/domain/, pure Dart)
                          │                                  ▲
                          └──►  Data/Services (lib/data/) ───┘
```

- `lib/core/` (`constants.dart`, `palette.dart`, `theme.dart`) is the only home for color constants (`kPalette`, `kSymbols`) and the theme.
- `tool/` contains only offline scripts (`generate_levels.dart`). `test/` mirrors `lib/`.
- Imports: **use relative imports inside `lib/`** (`../domain/game_rules.dart`); **use `package:up_water_sort/...` in `tool/` and `test/`**.

## 4. Code conventions

- Run `dart format` before committing; follow `flutter_lints`; file names `lower_snake_case.dart`, classes `UpperCamelCase`, members `lowerCamelCase`.
- `const` constructors whenever possible; prefer `final`; standard enums: `GameStatus`, `Sfx`, `HapticKind`.
- Intermediate models: `typedef Tubes = List<List<int>>` in `move.dart`; `Move(from, to, count)`; `LevelData` JSON fields `colors` (mapped to `colorCount`) and `par`.
- For every rules change: **write/update the unit test first** in `test/game_rules_test.dart`, then change the implementation.
- Do not hardcode display strings in widgets once i18n is enabled (see §10 for the mechanism to be decided).
- Never add a dependency on your own: check `flutter pub outdated`, and ask the user for any package outside the list in `PLAN.md` §5.

## 7. Testing

- Top priority: unit tests for `game_rules.dart`, `solver.dart`, `level_generator.dart` (pure domain → fast tests, no widget binding needed).
- Solver test: applying each `Move` of the solution in order must yield `isWon == true`; unsolvable levels return `null` within the node limit.
- Generator test: 20 different seeds → each color has exactly `capacity` units, no tube is already solved at start, and `Solver.solve` finds a solution.
- Controller test: select → pour → `moves == 1`; undo restores the exact state; win records stars (use a fake `StorageService` and `SharedPreferences.setMockInitialValues({})`).
- Widget test: `TubesBoard` renders the right number of tubes, tap triggers `onTubeTap`.
- Manual checks before release (`PLAN.md` §19.4): airplane mode on the first 10 levels, kill/relaunch, color-blind mode, ~5" phone and tablet, sound/haptics, light/dark theme.

## 8. Edge cases that must not regress (`PLAN.md` §18)

- Rapid taps during animation → ignored via `busy`; Undo disabled while `busy`.
- Tap an empty tube with nothing selected → ignored; tap the selected tube again → deselect; tap an invalid target **that contains liquid** → move selection to it; invalid empty/full target → error sound + haptic, **keep** the current selection.
- No legal moves left → `status = stuck` with Undo / Add tube / Restart; `addExtraTube` is **once per level**, the extra tube is always last in the list and is not recorded in `history` (so undo stays correct).
- App backgrounded mid-animation → `WidgetsBindingObserver` cancels the animation and **commits state immediately**.
- Corrupt save data → safe reset; running out of bundled levels → congratulations screen, no crash.

## 9. Forbidden (anti-patterns)

Adding network packages · importing Flutter into `lib/domain/` · mutating `Tubes` in place · Riverpod/Bloc/GoRouter/Flame · calling services from widgets · committing state before the animation ends · running the solver on the main isolate · hand-editing `levels.json` · changing save JSON keys without a migration · adding the `INTERNET` permission · debug `print` in release · committing keystores / `key.properties` / secrets · inventing features outside `PLAN.md`.
